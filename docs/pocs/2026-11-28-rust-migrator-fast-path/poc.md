# Serverless Migrator Fast Path

In Elastic Cloud Serverless, each project runs user serving (`ui`) and background task (`background_tasks`) Deployments plus a short Kubernetes Job (`kb-migrator-kb`) managed by the Serverless Kubernetes operator (`kibana-controller`). Kibana assigns pod behavior via node roles and forbids combining the `migrator` role with other roles. Whenever an image rollout, certificate or secret rotation, or config change alters the Job's hashed specification (the migrator Job hash), `kibana-controller` rolls out serving Deployments first and then runs `kb-migrator-kb`. Overall project reconciliation reporting finishes only after `kb-migrator-kb` exits.

Serving pods handle Saved Objects (Kibana's stored dashboards, visualizations, alerts, and configuration documents in Elasticsearch) index setup and update Kibana Data Streams (append only backing indices owned by observability significant events, AI evaluations, and workflows) on startup, while `kb-migrator-kb` runs afterward for document conversions and projects scaled to zero replicas.

Where we are: Every `kb-migrator-kb` Job boots the full Kibana Node.js server and all 164 to 188 enabled plugins before exiting prior to HTTP server start (28.9 s median uptime, 345 MiB memory, roughly 1 CPU core despite a 125 millicore request), even though over 99% of runs perform no document conversion.
Where we'll be: Every `kb-migrator-kb` Job first runs a lightweight, read only Node.js preflight verifier using a compact build time version manifest (targeting under 500 ms median wall time, under 300 ms CPU, and under 150 MiB memory in production sized containers) and exits 0 on verified noops, replacing itself with full Kibana only when a write, conversion, or unexpected state occurs.

## Why
Serverless production monitoring on November 28, 2026 (1 hour of 1 minute time weighted Kubernetes pod metrics) shows the fleet averages 31,552 Kibana pods consuming 829.7 continuous CPU cores and 16.42 TB of memory while completing roughly 2,473 migrator Jobs per hour. Steady state migrator load is small: 15.2 continuous cores (1.8% of fleet CPU) and 6.0 GB of memory (0.04% of fleet RAM). This work is not a standing memory cost fix.

The operational target is burst load during fleet wide stateless releases (image rollouts with no Saved Object schema changes) and cluster wide certificate or secret rotations across roughly 16,500 projects. Each migrator pod requests 125 millicores of CPU yet burns nearly 1 full core (an 8x burst ratio) during its 28.9 s median (48.1 s p95) plugin boot. Extrapolating 16,500 projects burning 1 core for 28.9 s over a 30 minute wave estimates 200 to 250 concurrent burst cores. Colocated serving pod throttling is currently inferred from that burst ratio rather than measured from a throttling incident, while the 28.9 s boot directly delays project reconciliation reporting after serving Deployments finish.

In a 1 hour sample of 500 `kb-migrator-kb` completion logs on November 28, 2026, actual migration work took 189 ms at the median and 99.4% finished in under 10 s without entering document conversion. A 24 hour OpenTelemetry migration duration histogram across all node roles (991,284 index migrations, including serving pods that skip document conversion) similarly shows 99.77% under 10 s.

Current monitoring does not yet isolate the share of the 2,473 hourly Jobs from rotations versus stateless releases versus project creations, the share of releases that have zero schema changes, the share of projects scaled to zero replicas, or measured colocated pod CPU throttling during peak waves. Measuring those inputs is Gate 1 of this proof of concept before building production rollout plumbing.

## End result
When this work is done, Serverless `kb-migrator-kb` containers verify Saved Objects state read only before booting full Kibana:

- Build time version manifest: Serverless image packaging adds a build step that boots Kibana in Serverless production context (image builds do not boot Kibana today) using Kibana's Saved Object snapshot tooling to emit a compact version manifest (~26 KB versus ~11 MB for full mappings, kept out of version control). The manifest maps core and plugin Saved Object types to their target index prefixes, latest model versions, owning plugin groups, enablement paths, Serverless defaults, full transitive required plugin dependencies (including dependencies that own no Saved Object types), base root index fields (shared index envelope fields outside per type mappings), removed types, and work in progress types (unreleased types full Kibana rejects unless explicitly allowed).
- Conditional registration guardrails: Continuous integration extends Kibana's existing conditional Saved Object registration lint rule to catch early return control flow and helper function indirection. Default off or inline suppressed conditional registrations are not modeled in the manifest (since snapshot validation does not test them), so any project enabling a conditional registration flag, deprecated enablement alias, or active work in progress type fails closed to full Kibana.
- Launcher dispatch and safe handoff: Inside the Kibana launcher script (after environment variables are translated into CLI flags and Node.js hardening plus cryptographic compliance settings are loaded), the preflight runs when the Serverless manifest exists, the migrator role environment variable indicates migrator only mode, and the `kibana-controller` rollout toggle environment variable is enabled. The preflight starts with a non zero default exit code and strict unhandled rejection handling so crashes cannot exit 0 silently. Only exit code 0 ends the Job as a verified noop. Termination signals propagate cleanly without booting full Kibana during pod teardown, and any other non zero exit replaces the launcher (`exec`) with full Kibana using the original arguments and zero resident preflight memory.
- Configuration and type resolution: The preflight reuses Kibana's configuration stack loader, encrypted keystore reader, and full TLS certificate loader (failing closed on password protected keystores), confirms the resolved node role is strictly migrator only, permits standard Serverless plugin group allowlisting and Zero Downtime settings (in place mapping and document updates without reindexing), and fails closed on unexpected migration or plugin overrides. Combining project config with the manifest yields the exact active types and target index prefixes.
- Read only exact match checks: Using a transport enforced `GET` only client, the preflight exits 0 only when every active index uses Zero Downtime format, matches base root fields (CI snapshot checks enforce model version bumps on per type mapping changes), matches both stored mapping versions (advanced by serving pods) and stored document versions (advanced by `kb-migrator-kb`) exactly across active types, has zero stored type names absent from the manifest (manifest known disabled plugins and removed types are excluded from equality checks), has both the global alias and current Kibana version alias (attached on version bumps) on that index, and has no alias across the prefix pointing to multiple indices.
- Data Streams deferral: The fast path skips Kibana Data Streams checks and writes, leaving all 9 registered streams to serving pods on startup. On projects scaled to zero replicas, same version stateless releases and rotations take the fast path and defer Data Streams updates until the first serving pod wakes up (Kibana version bumps miss the new version alias and fall back to full Kibana).
- Observability parity: On a verified noop, the preflight runs one parallel cluster info query alongside index reads so Elastic Common Schema (ECS) JSON stdout logs include full migration dashboard identity fields (including cluster identity, service version, node role, execution path, and duration) and exports per prefix OpenTelemetry Protocol (OTLP) migration duration metrics honoring Kibana's configured exporter protocol, temporality, and resource attributes (without adding cardinality shifting labels to the existing metric), flushed with a 1 s nonfatal exit timeout. Fallback runs log the structured fallback reason and suppress preflight OTLP duration export so full Kibana does not double record migration metrics.

To count as proven, the proof of concept must pass three gates:
1. Telemetry audit (before production rollout plumbing): Correlate `kb-migrator-kb` Job logs with `kibana-controller` reconciliation reasons, release metadata, project replica counts, and node CPU throttling metrics during a fleet wave to measure (a) the trigger split across rotations, stateless releases, and project creations, (b) stateless versus schema changing release frequency, (c) active versus scaled to zero project share, and (d) actual wave CPU throttling or reconciliation completion impact. Pass requires measurable wave contention or reconciliation delay and at least 20% of burst Jobs coming from stateless releases.
2. Production sized container benchmark: On a Serverless class Linux ARM64 node under production limits (125 millicores CPU request, 1 CPU limit, 2 GiB RAM), across 30 fresh container runs against a warm local Elasticsearch mock covering all four Serverless profiles (`es`, `oblt`, `security`, `vectordb`) with full config stacking, TLS verification, ECS logging, and deployed OTLP export wired: median wall time under 500 ms (p95 reported), CPU under 300 ms, and peak memory under 150 MiB. Earlier unconstrained prototypes without full config or telemetry measured 65.8 ms / 63.7 ms CPU / 82.8 MiB RAM in Node.js 24 and 35.5 ms / 25.3 ms / 9.5 MiB in Rust (recorded in this folder's benchmark notes).
3. Functional parity verification: End to end container tests pass across all four Serverless project profiles with zero false noops on exact match, lagged document versions, version mismatches, root field drift, missing indices or aliases, multi index alias collisions, disabled plugin metadata, unrecognized stored type names, active work in progress or conditional flags, transitively disabled plugins, and clean launcher handoff preserving full Kibana exit codes, arguments, and termination signals.

We would stop or pivot if Gate 1 finds negligible burst contention and reconciliation impact (stop), if non image rotations exceed 80% of migrator bursts (pivot to controller Job hash decoupling first), if full parity Node.js wiring exceeds 500 ms wall time, 300 ms CPU, or 150 MiB memory under production limits (pivot to a leaner OTLP emitter or swap in the compiled Rust runner behind the same manifest and launcher contract), or if canary telemetry shows serving pod readiness races causing over 20% missing index or missing alias fallbacks (triggering a serving pod status startup probe fix in `kibana-controller`).

Explicitly out of scope for v1: any Elasticsearch writes in the fast path, updating Kibana Data Streams inside the fast path, lowering migrator pod resource limits or removing the diagnostic heap snapshot volume (mounted for out of memory dumps, still needed because fallback runs full Kibana under 2 GiB RAM and 1 CPU limits), non Serverless distributions (Elastic Cloud Hosted, self managed, Elastic Cloud on Kubernetes, and hardened government images), legacy `v2` migrations (older reindex and alias swap format), shipping a production Rust binary or cross compilation pipeline, and eliminating Kubernetes Job creation in `kibana-controller`.

- Given a Serverless project whose active Saved Object indices are up to date with matching base root fields, exact matching stored mapping and document versions, and clean single index global and version aliases, when `kb-migrator-kb` runs with the rollout toggle enabled across 30 fresh production sized container runs against a warm local Elasticsearch mock, then each run verifies read only, emits ECS completion logs and per prefix OTLP metrics, and exits 0 with median wall time under 500 ms, CPU under 300 ms, and memory under 150 MiB without booting Kibana plugins.
- Given a Serverless project rolled back to a prior same version stateless release whose expected versions match stored mapping and document versions and whose version alias already exists, when `kb-migrator-kb` runs, then the preflight verifies exact equality and exits 0 without booting full Kibana.
- Given a Serverless project that needs a write, document conversion, or schema changing rollback, or hits a missing index or alias, alias collision, legacy index, unrecognized stored type, active work in progress type, or Elasticsearch connection error, when `kb-migrator-kb` runs, then the preflight logs a structured fallback reason, suppresses preflight OTLP metric export, and exits non zero so the launcher replaces itself with full Kibana, which runs the migration or surfaces its normal fatal error and exits with full Kibana's status.
- Given a Serverless `ui` or `background_tasks` pod, a non Serverless Kibana image, or a Serverless migrator Job with the rollout toggle disabled, when the container starts, then the fast path is bypassed completely and full Kibana runs unchanged (while invalid multi role configurations containing migrator bypass the launcher when set via environment variable or fail closed from the preflight when set via configuration files so full Kibana reports its normal validation error).

## Decisions
1. Runtime and fast path architecture: Lightweight Node.js read only preflight verifier reusing Kibana's configuration, keystore, TLS, and version comparison code, invoked from the Kibana launcher script behind a runtime agnostic version manifest and exit code handoff. Running inside the launcher inherits hardening and cryptographic compliance settings plus translated CLI flags without duplicating wrapper logic, skips loading Kibana's tracing agent preload on noops, frees all preflight memory on fallback, and keeps a clean swap point if production telemetry ever justifies a compiled Rust binary. Fails when: full parity wiring exceeds 500 ms wall time, 300 ms CPU, or 150 MiB memory under production limits, or production burst metrics show Node's startup cost still causes contention. Alternatives:
   - Compiled Rust read only preflight: Fastest prototype runtime (35.5 ms wall, 25.3 ms CPU, 9.5 MiB memory), deferred as an optional drop in swap because 15.2 steady cores and estimated 200 to 250 core bursts do not justify a second production language toolchain before proving the manifest and rollout model.
   - Full Rust migration wrapper: Reimplements Elasticsearch index, mapping, and alias writes alongside an 11 MB mappings bundle in Rust. Lost due to high drift risk against upcoming `v3` migrations (an unmerged Kibana proposal tracked outside this branch to unify `v2` and Zero Downtime migrations) when serving pods already handle index setup on most runs.
   - Controller Job hash decoupling: Excludes certificates, trust bundles, shared secrets, and unrelated config from the migrator Job hash in `kibana-controller`. Deferred as a complementary follow up (promoted ahead of Kibana work if Gate 1 proves rotations exceed 80% of bursts), because it removes rotation Jobs but still boots full Kibana on every stateless image release and project creation.
   - Controller build fingerprint gate: Attaches a build time migration fingerprint to container images so `kibana-controller` skips Jobs on stateless releases. Lost due to cross repo coupling across builds, promotion, and `kibana-controller`, container registry outage risk during reconciliation, hash migration storm risk, and loss of failed Job self healing on config or secret fixes.
   - Hybrid live serving pod migration probe: Fixes serving pod readiness to wait for Saved Objects initialization, exposes pending document migration status from active serving pods, and lets `kibana-controller` skip `kb-migrator-kb` on active projects while still spawning Jobs when document migration is pending or replicas are zero. Lost for v1 to avoid controller to pod internal HTTP networking and keep uniform coverage across active and scaled to zero projects, though Gate 1's active versus scaled to zero split lets us revisit if active projects dominate and stream owners reject deferral.
   - Split migration only plugin entrypoint: Refactors roughly 50 to 70 plugins that register Saved Object types so Kibana boots a migration only subset without loading full server services. Lost for v1 due to cross team lead time, even though it removes manifest drift and also accelerates real document conversion waves and Elastic Cloud Hosted.
   - Status quo with ongoing bundling and `v3` migrations: Waits on unmerged server plugin bundling (an active bundling effort tracked outside this branch, reported at 22.7% warm start boot CPU reduction), deferred plugin initialization (which runs after HTTP server start and therefore after `kb-migrator-kb` already exits), and upcoming `v3` migrations. Lost because estimated 200 to 250 core bursts and the 28.9 s tail remain largely unaddressed.
2. Rollout gating and `kibana-controller` scope: Add a migrator only rollout toggle (default off, opt in per environment or project) excluded from the Job identity hash plus a separate operator set rerun token (included in the hash) in `kibana-controller`. Excluding the toggle lets canary ramp and emergency kill switch disable apply to subsequent Jobs without rolling serving Deployments or causing a Job storm. Including the separate rerun token (absent in `kibana-controller` today) lets operators force retroactive full Kibana reruns after a bad manifest without touching serving Deployments. Changing serving pod startup probes is deferred unless canary fallbacks exceed 20%. Fails when: `kibana-controller` release bandwidth blocks delivery. Alternatives:
   - Image and release channel rollout only (zero `kibana-controller` changes): Lost because disabling a misbehaving fast path on one project or cluster would require reverting the entire Kibana release.
   - Including the rollout toggle inside the migrator Job hash: Lost because enabling or pulling the kill switch would launch an unthrottled fleet wide wave of migrator Jobs.
   - Manual Job deletion instead of a rerun token: Lost because deleting Jobs does not clear the controller's observed migration status cleanly or scale across clusters during an incident.
   - Preemptively changing serving pod startup probes before canary: Lost because adding startup probe risk to serving Deployments before measuring actual canary readiness race fallback rates is premature.
3. Fast path scope, strict equality, and Data Streams handling: Restrict the fast path to strict exact match read only Saved Objects checks (failing closed on version inequalities, including schema changing rollbacks) and leave Data Streams to serving pods without disabling them in shared config (which governs serving pods and fallback). Data Streams have no document conversion or role split, so serving pods update all 9 streams on startup. Exact equality shrinks the manifest from 11 MB to 26 KB, removes rollback edge cases, and avoids duplicating workflows' dynamic retention rules. Fails when: readiness races cause over 20% canary fallbacks without a startup probe fix, or stream owners require migrator Jobs to update scaled to zero projects immediately. Alternatives:
   - Supporting rollback version inequality inside the fast path: Lost because same version stateless rollbacks already satisfy exact equality and rollbacks crossing newly added types already fall back, so inequality branching adds high false noop risk for rare cases.
   - Read only Saved Objects check plus read only Data Streams verification: Lost because tracking workflows' runtime retention settings adds drift risk for work serving pods already execute.
   - Including Elasticsearch index and alias writes in the fast path: Lost because bundling full mappings and duplicating write state transitions creates high drift risk ahead of upcoming `v3` migrations.
4. Manifest completeness and Elasticsearch failure policy: Generate the manifest during Serverless image packaging by booting Kibana in Serverless production context with the snapshot tooling, extend Kibana's existing conditional registration lint rule to catch early returns and helper indirection, and fail closed on any unmodeled conditional flag, deprecated enablement alias, active work in progress type, or Elasticsearch connection error (delegating long cluster warmup waits to full Kibana's existing retry loop). Fails when: build extraction adds unacceptable packaging time or transient Elasticsearch blips cause excessive canary fallbacks (justifying one short retry). Alternatives:
   - Static manifest declaration in every plugin metadata file: Lost due to manual duplication and cross team migration effort across dozens of plugins.
   - Runtime multi profile CI comparison without failing closed on default off flags: Lost because default Serverless profile configs do not enable per project opt in flags.
   - Multi second warmup retry loop inside the preflight: Lost because waiting several seconds inside a sub 500 ms preflight duplicates full Kibana's Elasticsearch readiness loop.
5. Observability parity: Emit full ECS JSON stdout logs (including cluster identity via one parallel cluster info query) and per prefix OTLP migration duration metrics via a scoped OTLP emitter matching Kibana's configured protocol, temporality, and resource attributes (without adding custom labels to the existing duration metric or importing the full server metrics graph if it blows budget), flushed with a 1 s nonfatal exit timeout and ramped gradually from canary to full fleet. Fails when: OTLP export exceeds the 500 ms wall, 300 ms CPU, or 150 MiB memory budget, forcing a leaner protocol emitter or a swap to the Rust runner. Alternatives:
   - ECS JSON logs only (skipping OTLP metrics on fast path noops): Lost because dropping 2,473 duration recordings per hour distorts migration time histograms and risks tripping automated metric drop alerts.
   - Omitting cluster identity from fast path ECS logs: Lost because omitting cluster identity risks breaking migration dashboards that filter or group by cluster.
6. External approvals and rollout sequencing (open): Two cross team items remain open and block production canary enablement (they do not block Gate 1 telemetry audit, proof of concept implementation, or staging benchmarks):
   - `kibana-controller` team scheduling for the hash excluded migrator only toggle and the separate migrator rerun token.
   - Sign off from observability significant events, AI evaluations, and workflows Data Streams owners accepting that scaled to zero projects defer Data Streams updates on same version releases and rotations until the first serving pod wakes up.

## Risks and assumptions
- Security, TLS, and credential handling: The preflight holds full Kibana Elasticsearch credentials across service account tokens, basic auth, encrypted keystores, custom certificate authorities, and client certificates. Invoking via the Kibana launcher preserves Node.js hardening and cryptographic compliance flags, reusing Kibana's full PEM and PKCS#12 TLS loader (failing closed on password protected keystores) prevents verification drift, a transport level `GET` only guard enforces read only safety technically rather than by convention, fallback logs must redact credentials, and missing or corrupt manifests fail closed to full Kibana.
- Readiness race on new projects and Kibana version bumps: In Serverless, Kibana disables its interactive preboot UI server and instead runs a temporary startup HTTP listener that returns HTTP 503 to all user traffic while still answering HTTP 200 to the internal event loop endpoint polled by `kibana-controller`'s default Kubernetes readiness probe. Because new projects need initial indices and Kibana version bumps need a new version alias, `kb-migrator-kb` can start before serving pods finish Saved Objects initialization. Failing closed keeps this safe, though canary fallback rates above 20% would require adding a serving pod status startup probe in `kibana-controller`.
- Scaled to zero deferral behavior: Leaving Data Streams to serving pods assumes stream owners accept that projects scaled to zero replicas defer updates on same version releases and rotations until first serving pod wakeup. User requests stay blocked by the temporary HTTP 503 startup listener until both Saved Objects and Data Streams finish initializing, though broken stream updates, invalid plugin config schemas, and Elasticsearch startup checks (such as scripting availability) on scaled to zero projects surface on wakeup rather than in `kb-migrator-kb`.
- Automated alert volume drops: Skipping full Kibana boot removes roughly 99% of migrator startup log volume (2,473 boots per hour). Rollout must ramp gradually by environment and channel so automated anomaly detection alerts for low log and metric volume adapt without paging on call.
- Node.js dependency and plugin enablement drift: Importing heavy core server or full OpenTelemetry SDK graphs would blow the 500 ms / 300 ms / 150 MiB budget, while static plugin enablement resolution without plugin schemas must fail closed whenever deprecated enablement aliases or conditional defaults are encountered. Production sized container benchmarks verify the budget before rollout, with the Rust runner available behind the same contract if Node exceeds limits.
- Trigger mix uncertainty and rollback discipline: Until Gate 1 measures the actual trigger mix, release frequency, scaled to zero share, and wave throttling, burst reduction remains an estimate. Emergency rollback disables the toggle cleanly for future Jobs without triggering a storm, and retroactive full Kibana reruns use the separate controller rerun token.
