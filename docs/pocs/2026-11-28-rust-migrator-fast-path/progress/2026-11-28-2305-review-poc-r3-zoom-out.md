Severity: Major
Where: `## Decisions` — Decision 1, "Live serving pod migration probe" (line 51)
Finding: False compromise. Decision 1 dismisses querying running serving pods to skip creating `kb-migrator-kb` because *"it cannot cover projects scaled to zero replicas and current serving pod readiness passes before Saved Objects initialization finishes."* Both objections treat an avoidable structure as an all-or-nothing tradeoff: (1) the readiness-probe bug is shared by the chosen preflight—Risk 2 (line 72) and Decision 2 (line 54) admit version-bumping stateless rollouts hit the exact same race because `config/serverless.yml:109` disables full preboot while `src/core/packages/root/server-internal/src/server.ts:266-273` serves 200 on the ELU endpoint (`metrics_service.ts:84-88`) before `/api/status` leaves 503 (`status_preboot.ts:43-45`), and Decision 2 already proposes evaluating a serving-pod startup probe fix in `kibana-controller`; (2) covering scaled-to-zero projects does not preclude skipping the Job on active projects. A hybrid structure removes the compromise: fix the serving-pod startup/readiness probe to wait on `/api/status`, have serving pods run the existing pure `checkVersionCompatibility(..., { source: 'docVersions' })` check (`src/core/packages/saved-objects/migration-server-internal/src/zdt/utils/check_version_compatibility.ts:37`) against the mapping already fetched in `init.ts:74` to expose whether document migration is pending, and have `kibana-controller` skip spawning `kb-migrator-kb` when a rolled serving pod reports no document migration needed—launching the existing `kb-migrator-kb` Job only when document migration is pending, the probe fails, or `replicas == 0`. That removes the build-time manifest, plugin-graph reimplementation, CI conditional-registration analyzer, launcher wrapper, parallel ECS/OTLP stack, Kubernetes Pod scheduling overhead on active projects, and Data Streams deferral on scaled-to-zero projects (eliminating the Decision 6 stream-owner approval blocker). Its own cost is adding an authenticated/internal HTTP check from `kibana-controller` to serving pods during reconciliation and leaving scaled-to-zero projects on full `kb-migrator-kb` (so burst savings depend on the unmeasured active-vs-scaled-to-zero split).
Suggestion: Measure the active-vs-scaled-to-zero project split in Gate 1 and evaluate the hybrid serving-pod probe (with `kb-migrator-kb` fallback for `replicas == 0`) directly against the in-container manifest architecture.

Severity: Major
Where: `## Decisions` — Decision 1 ("Controller Job hash decoupling", line 49), Decision 2 (line 54), and `## Risks and assumptions` (line 72)
Finding: Root cause. The design builds a parallel manifest, static-analysis, and preflight stack inside the container while leaving all upstream causes untouched: `kibana-controller` hashing certs/secrets/unrelated config into the migrator Job hash, `kibana-controller` polling the ELU endpoint instead of `/api/status`, and Kibana's `migrator` role still executing `plugins.setup()` across all 164–188 plugins and `dataStreams.start()` before immediately exiting (`src/core/packages/root/server-internal/src/server.ts:514-626`). Decision 2 already puts `kibana-controller` changes on the critical path (rollout toggle and rerun token, blocked on controller scheduling in Decision 6), and Risk 2 concedes that without fixing the serving-pod startup probe, version-bumping stateless rollouts can exceed 20% fallback and lose the burst win—yet Job hash decoupling is deferred unless rotations exceed an arbitrary 80% threshold (lines 36, 49) and the startup probe fix is only *"evaluate[d]"* (line 54). Meanwhile, on every schema-changing fleet release (even one Saved Object model version bump), the fast path falls back on 100% of projects and leaves the 200–250 core burst untouched.
Suggestion: Since `kibana-controller` changes are already required, sequence the serving-pod startup probe fix and migrator Job hash decoupling ahead of (or independently from) building an in-container manifest and preflight system.

Severity: Major
Where: `## End result` (lines 33, 36), `## Decisions` — Decision 1 (lines 46–47), Decision 5 (line 64–65), and `## Risks and assumptions` (line 75)
Finding: Premature optimization and YAGNI. First, the hard pivot budget of under 500 ms median wall time, 300 ms CPU, and 150 MiB peak memory—which triggers building a custom leaner OTLP exporter or swapping in a compiled Rust binary (lines 36, 46, 64, 75)—has no measured operational need behind it. Against a 28.9 s / 1-core / 345 MiB baseline and a 2 GiB container limit that is out of scope to reduce (line 38), even a 1–2 s / 200 MiB Node.js preflight reusing Kibana's existing `@kbn/metrics` (`src/platform/packages/private/opentelemetry/kbn-metrics/src/init_metrics.ts`) and `@kbn/telemetry` (`build_otel_resources.ts`) cuts burst CPU by ~95% (200–250 cores down to ~10 cores) and stays well below the 2 GiB limit and Kubernetes Pod startup latency. Second, designing the manifest and shell handoff as *"runtime agnostic"* to *"keep a clean swap point if production telemetry ever justifies a compiled Rust binary"* (line 46) introduces an abstraction for a Rust toolchain that Decision 1 itself calls unjustified (line 47) and out of scope (line 38); note also that skipping APM preload on noops does not by itself require shell-level process dispatch, since APM is loaded inside `src/cli/kibana/dist.js:11` before core bootstrap. Suggestion: Base the performance gate on the operational burst-reduction target rather than an arbitrary 500 ms / 150 MiB cutoff, drop the Rust swap-point requirement from v1, and verify whether any OTel low-count alert exists before requiring in-preflight OTLP export.
