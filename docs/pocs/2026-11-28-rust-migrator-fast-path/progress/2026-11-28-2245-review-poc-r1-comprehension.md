## How the system works today, per this document

In Elastic Cloud Serverless, `kibana-controller` runs a short Kubernetes Job (`kb-migrator-kb`) after every Kibana rollout, certificate or secret rotation, or configuration change to verify Saved Objects in Elasticsearch and convert documents when schemas advance. Every run boots the full Kibana Node.js server and 164 to 188 plugins—taking 28.9 s at the median (48.1 s p95), 345 MiB of memory, and roughly 1 full CPU core despite requesting 125 millicores—even though actual migration work takes 189 ms at the median and 99.4% of runs perform no document conversion. Steady-state migrator load across ~2,473 Jobs per hour is small (15.2 continuous cores, 6.0 GB RAM), but fleet-wide stateless releases and cert/secret rotations across ~16,500 projects launch simultaneous waves bursting to 200–250 concurrent cores that contend with colocated `ui` and `background_tasks` pods and delay rollout completion reporting. Meanwhile, `ui` and `background_tasks` pods already perform most Saved Object index setup and update all 9 Kibana Data Streams on startup, while `kb-migrator-kb` emits ECS JSON logs used by migration dashboards and OTLP duration metrics monitored by PagerDuty machine learning alerts.

## What this proposes

During Serverless image packaging, the build will extract a ~26 KB version manifest (excluded from version control) recording every Saved Object type's target index prefix, latest model version, owning plugin, plugin group, required dependencies, conditional feature flags, base root index fields, and removed types, paired with a lint check closing an early-return registration bypass. A new default-off, migrator-only rollout toggle in `kibana-controller` will direct Serverless containers running only the migrator role to execute a lightweight, read-only Node.js preflight verifier instead of booting full Kibana. The preflight will load Kibana's full Serverless configuration stack, resolve active Saved Object types, query Elasticsearch read-only once per active index prefix, and—when every index is in Zero Downtime format with matching base root fields, zero unrecognized metadata keys, and either exact version/alias matches or a valid rollback—emit ECS JSON logs and OTLP duration metrics and exit 0 (targeting under 500 ms wall time, 300 ms CPU, and 150 MiB RAM). On any required write or unexpected state, the preflight logs a structured fallback reason and launches full Kibana inside the same container (retaining 2 GiB RAM / 1 CPU limits and leaving Data Streams to `ui` and `background_tasks` pods), while keeping the manifest and container dispatch runtime-agnostic so an already-prototyped Rust binary can drop in later if Node exceeds budget.
