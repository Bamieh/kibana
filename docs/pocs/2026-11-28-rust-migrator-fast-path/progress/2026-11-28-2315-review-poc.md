## Latest Comprehension Reader Paraphrase (Round 3, verbatim)

### How the system works today, per this document

In Elastic Cloud Serverless, `kibana-controller` manages each project's `ui` and `background_tasks` serving Deployments plus a short `kb-migrator-kb` Kubernetes Job. Whenever an image rollout, certificate or secret rotation, or config change alters the migrator Job hash, `kibana-controller` rolls out the serving Deployments first—where serving pods set up Saved Objects indices and mappings and update Kibana Data Streams—and then runs `kb-migrator-kb` to handle document conversions and projects scaled to zero replicas, finishing project reconciliation reporting only after the Job exits. Every `kb-migrator-kb` run boots the full Kibana Node.js server and all 164 to 188 enabled plugins (28.9 s median uptime, 345 MiB memory, roughly 1 CPU core despite a 125 millicore request), even though over 99% of runs finish migration work in under 10 s (189 ms median) without entering document conversion. Steady-state fleet migrator load is small (15.2 continuous cores), but fleet-wide stateless image releases and certificate or secret rotations across roughly 16,500 projects create an estimated 200 to 250 concurrent core burst and add a 28.9 s tail to reconciliation reporting, though monitoring does not yet separate the share of the 2,473 hourly Jobs coming from rotations versus stateless releases versus project creations.

### What this proposes

First, a Gate 1 telemetry audit will measure the trigger split across rotations, stateless releases, and project creations plus wave CPU throttling, pivoting to `kibana-controller` Job hash decoupling first if non-image rotations cause over 80% of bursts. Otherwise, Serverless Kibana images will package a compact (~26 KB) build-time Saved Object version manifest—backed by CI static checks on registration calls—and the Kibana launcher will run a lightweight, read-only Node.js preflight verifier before booting full Kibana whenever the manifest exists, the migrator-only environment variable is set, and a new hash-excluded `kibana-controller` rollout toggle is enabled. The preflight reuses Kibana's configuration, keystore, and TLS builders to verify read-only exact-match Saved Objects index, version, and alias invariants against Elasticsearch, skips Kibana Data Streams (deferring updates on scaled-to-zero projects until a serving pod wakes up), emits matching ECS logs and per-prefix OTLP duration metrics, and exits 0 (targeting under 500 ms wall time, 300 ms CPU, and 150 MiB memory) when no write is needed. On any mismatch, missing index or alias, connection error, or unexpected state, it exits non-zero so the launcher replaces itself (`exec`) with full Kibana; `kibana-controller` also gains an explicit rerun token for retroactive full runs and an evaluation of a serving pod status startup probe for readiness races.

- **FIX (Major — `critic` M2):** Required overriding `--unhandled-rejections=warn` (defaulting to non-zero exit code + throwing on unhandled rejections) so crashes cannot silently exit `0`, and trapping/propagating termination signals (`SIGTERM`/`SIGINT`, exit codes >= 128) in the launcher so pod teardown never boots full Kibana.
- **FIX (Major — `critic` M1, `zoom-out` M4 & M5, `comprehension` M2):** Stated explicitly that image builds do not boot Kibana today (manifest packaging boots Kibana in Serverless production context), extended the existing conditional-registration lint rule rather than building a parallel CI analyzer, and forced fail-closed on default-off/inline-suppressed conditional flags, deprecated enablement aliases, and active WIP types.
- **FIX (Major — `critic` M3, `comprehension` M3):** Required zero multi-index collisions across *every* alias on the prefix (matching ZDT `getAliases`), and aligned version-alias creation to Kibana version bumps (clarifying that scaled-to-zero projects fast-path same-version releases and rotations, while falling back on version bumps).
- **FIX (Major — `comprehension` M4, `critic` M6):** Resolved startup-probe sequencing by deferring any serving-pod startup-probe change unless canary fallback rates exceed 20% (removing it from pre-canary blockers in Decision 6), explained the rerun token hash mechanic and rejected alternatives in Decision 2, and weighed CI verification alternatives in Decision 4.
- **FIX (Major — `critic` M9):** Replaced discipline-only read-only safety with a transport-enforced `GET`-only HTTP guard in the preflight Elasticsearch client, and included full PEM/PKCS#12 TLS loading (failing closed on password-protected keystores).
- **FIX (Major — `zoom-out` M1 & M2, `critic` M7):** Added explicit Gate 1 stop/pass thresholds (measurable burst/reconciliation impact, >=20% stateless-release burst share, stateless release frequency, active vs scaled-to-zero share), noted the 24h OTel histogram covers all roles, specified OTLP suppression on fallback runs to prevent double recording, and explicitly weighed the hybrid live serving-pod probe (active pods + `kb-migrator-kb` fallback for `replicas == 0`) in Decision 1.
- **FIX (Major — `comprehension` M6, M7, M8, M10; `critic` M4, M8):** Glossed remaining Kibana startup/storage terms (`node roles`, temporary HTTP 503 startup listener vs disabled preboot UI, base root index fields, global vs version aliases, APM preload, WIP types), fixed Scenario 4 env-vs-config multi-role dispatch wording, and aligned `Where we are:` / `Where we'll be:` from the Round 3 comprehension paraphrase.
- **CONTEST (Major — `zoom-out` M3: sequence `kibana-controller` Job hash decoupling and startup probe fix ahead of Kibana preflight regardless of Gate 1):** Contested with evidence: Gate 1 already precedes production rollout plumbing and pivots to controller Job hash decoupling first if rotations exceed 80% of bursts. Prioritizing hash decoupling unconditionally before Gate 1 would leave stateless image releases booting full Kibana across ~16,500 projects if releases prove to be a major burst driver, and preemptively changing serving-pod probes before measuring actual canary readiness-race fallbacks adds Deployment rollout risk without evidence.
- **CONTEST (Major — `zoom-out` M6: drop the runtime-agnostic Rust swap boundary and relax the 500 ms / 150 MiB budget to 1–2 s / 200 MiB):** Contested with evidence: the stakeholder explicitly chose in Decision 1 to preserve a clean manifest and launcher exit-code boundary so a compiled Rust runner remains a low-friction swap if production burst telemetry later justifies it. Invoking inside `bin/kibana` already reuses `bin/kibana_env` (FIPS/hardening flags) and `kibana-docker` CLI translation without duplication, skips APM preload on noops, frees 100% of preflight memory before full Kibana boots, and adds ~65 ms (<0.25%) to <1% fallback runs. Keeping the 500 ms / 300 ms CPU / 150 MiB PoC bar prevents silently pulling in heavy core/OTel graphs that would erode CPU savings.
- **DECLINE (8 Nits across R1–R3):** Remaining minor stylistic preferences (e.g., removing the Rust swap boundary as YAGNI in R1 `critic` N1; citing external internal dashboard URLs/queries inline in design-altitude prose; keeping minor Gate 3 parity scenarios concise vs separating every internal schema condition) were declined to keep `poc.md` at stakeholder design altitude while keeping detailed evidence in companion files (`explorations.md`, `benchmark-results.md`, `fleet-analysis-summary.md`).
