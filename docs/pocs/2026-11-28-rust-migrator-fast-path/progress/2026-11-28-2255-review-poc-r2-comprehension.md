## How the system works today, per this document

In Elastic Cloud Serverless, each of roughly 16,500 projects runs user-serving (`ui`) and background task (`background_tasks`) Deployments alongside a `kb-migrator-kb` Kubernetes Job managed by `kibana-controller`. Whenever an image rollout, certificate or secret rotation, or configuration change alters the migrator Job's hashed specification, `kibana-controller` updates the serving Deployments first, waits for them to roll out, and then runs `kb-migrator-kb`; serving pods perform Saved Objects index/mapping setup and update all 9 Kibana Data Streams on startup, while `kb-migrator-kb` performs document conversions and covers projects scaled to zero replicas. Every `kb-migrator-kb` Job boots the full Kibana Node.js server and 164 to 188 plugins—taking a 28.9 s median (48.1 s p95), 345 MiB memory, and nearly 1 full CPU core despite requesting 125 millicores—even though over 99% of runs perform no document conversion and actual migration work takes 189 ms at the median. Steady-state migrator usage across ~2,473 hourly Jobs is small (15.2 continuous cores, 6.0 GB memory), but simultaneous waves during stateless image releases and certificate or secret rotations burst to roughly 200 to 250 concurrent cores, contending with colocated serving pods and delaying rollout completion reporting.

## What this proposes

This PoC adds a lightweight, read-only Node.js preflight verifier to the Serverless container entrypoint that runs before full Kibana whenever a build-time Saved Object version manifest (~26 KB, generated by extending Kibana's snapshot tooling and checked by lint rules and CI runtime verification) is present, the container is in migrator-only mode, and a new hash-excluded `kibana-controller` rollout toggle is enabled. The preflight reuses Kibana's configuration stack, keystore, and TLS setup to determine active Saved Object types, queries each active index prefix read-only in Elasticsearch with bounded warmup retries, and checks Zero Downtime format, base root fields, stored mapping and document versions, and required Kibana version aliases while leaving Kibana Data Streams updates to serving pods. On a verified noop or valid rollback, it emits ECS JSON logs and OTLP gRPC duration metrics within a target budget of under 500 ms local overhead, 300 ms CPU, and 150 MiB memory and exits 0; on any required write, unexpected state, or error, it logs the fallback reason and exits with a dedicated status code so the wrapper replaces itself (`exec`) with full Kibana in the same container. The manifest and exit-code contract stay runtime-agnostic so a compiled Rust binary can be swapped in later without changing build extraction, `kibana-controller`, or observability contracts, and the PoC also plans to measure what share of hourly Jobs come from rotations versus stateless releases versus project creations.
